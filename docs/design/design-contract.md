## 0. One page summary

**Purpose.** Make every screen look polished and consistent from the first commit, by deciding the numbers once: spacing, widths, sizes, colour, states and rules. A screen is built by choosing a template, composing it from the component inventory, and passing the guard rails in section 12. If something you need is not here, stop and propose a change to this file. Do not invent a value.

**The look.** A quiet neutral shell. One product accent, Heed blue: the main button, focus, the selected place and row, checked controls and links. The logo, the chrome's surfaces, counts and badges never take it. Colour carries meaning only: five item kinds (orange event, blue note, green guide, violet example, and the warning-toned issue), a coloured domain mark for each domain, and four status hues that always appear with a shaped icon. Everything else is neutral.

**The numbers to remember.**

| Topic             | Decision                                                                                                                                                                                                                                                  |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Spacing           | 4, 8, 12, 16, 24, 32, 48, 64 pixels. Only parents set gaps. No margins on children. A lint rule enforces it (section 3)                                                                                                                                   |
| Shell             | Sidebar 256, rail 48, header 48 (56 on phones), toolbar 44. Below 1280 pixels the sidebar becomes the rail on its own                                                                                                                                     |
| Gutter and widths | One page gutter: 24 (16 below 768). Three content widths: full for lists, 1120 for overviews, 720 for forms and reading                                                                                                                                   |
| Density           | Grid rows 40 (compact, the default), 48 (comfortable) and 64 (with scope) under a 36 header. Controls 28, 32, 40; every target is 44 on phones                                                                                                            |
| Templates         | List page, document page, overview page. The page title lives once: in the header, or in the paper on a document page                                                                                                                                     |

| Shapes            | Interactive controls are 4 pixel rounded rectangles of one height per toolbar (6.4). Information tags are badges: 6 pixel rounded rectangles with a mark and a label (6.13)                                                                               |

**What changed from the HTML prototypes.** Section 2 lists each departure with its reason. The largest: statuses become shaped icons and a healthy item shows no colour; form fields get a 3:1 boundary (the prototypes had 1.4:1); the library is one continuous virtual list with no paging and no tab row; the assistant is a docked panel; avatars wear a soft tint from the person's id (6.14).

**What needs a person.** Section 13 lists the open design questions.

## 1. Authority, words and vocabulary

**Order of authority.** The requirements specification, then this contract, then the earlier HTML prototypes. The prototypes are the two plain HTML rounds the product owner reviewed: round 4 set the structure and density, round 5 the colour system. They are intent, not pixel specifications. Their structure, density, copy and colour carry over. Their individual pixel values do not.

**The research** in this contract means the front-end research done for this product: the toolkit choice, the guard rails and the standards for generated user interfaces.

**Changing the contract.** A change to a scale, a token, a template or a rule is one reviewed pull request that edits this file, the token file and the tests together. A screen pull request never changes the scale on its own.

**Requirement words.** Must, should and may mean what they mean in the requirements specification.

**The product's name.** A screen names the product only where the sentence needs it ("Sign in to Heed", "What is Heed"), never in a label that works without it: Back, Add to your agent, Last week, Ask first. Where it does, the name comes from one setting, `CL_PRODUCT_NAME` (`productName` in `src/web/lib/brand.ts`, `{{product}}` in a help page), so a rename is one change. Technical names that carry it (the `heed-*` marks below, the CLI, storage keys) stay until a rename migrates them (`docs/rename-checklist.md`).

**Words used here.**

| Word      | Meaning in this contract                                                                                             |
| --------- | -------------------------------------------------------------------------------------------------------------------- |
| Item      | One piece of context. The specification calls it a context item. The library lists items                             |
| Kind      | The type of an item. Five only (below)                                                                               |
| Domain    | A business area, shown as a label with a coloured domain mark. The specification's word is Area. See open question 2 |
| Status    | The state of an item or proposal, from the specification's states (below)                                            |

| Primitive | A layout component (`Stack`, `Cluster`) that sets a gap from the scale                                               |

## 3. Spacing

### 3.1 The scale

Base unit 4 pixels. Padding, gap and scroll padding may use only these steps. Margins are banned except `auto`.

| Pixels | Tailwind step | Typical use                                                                 |
| ------ | ------------- | --------------------------------------------------------------------------- |
| 4      | 1             | Icon to label inside a compact control, between a title and its hint        |
| 8      | 2             | Between sibling controls in a toolbar, label to field, inside menus         |
| 12     | 3             | Toolbar block padding, stack inside a card, heading to content in a section |
| 16     | 4             | Phone gutter, between fields, card padding, between cards                   |
| 24     | 6             | Desktop gutter, top space of an overview, space above the selection bar     |
| 32     | 8             | Between sections, top space of a document                                   |
| 48     | 12            | Large gaps in empty states                                                  |
| 64     | 16            | Scroll room under a document so the last field clears the action bar        |

### 3.2 Rules

1. **Only the scale.** Padding, gap and scroll padding take steps from 3.1 and `0`. Nothing else, including half steps such as `1.5` and `2.5`. Scroll padding may also use the named clearances `table-header` and `selection-clearance` (4.1).
2. **Only parents set gaps.** Space between siblings is the parent's `gap`. Children have no margins, so margins can never stack. The `Stack` (column) and `Cluster` (wrapping row) primitives take a `gap` prop limited to the scale.
3. **Padding belongs to the box that owns the surface.** A card pads itself. A child never adds padding to push away from a sibling.
4. **One horizontal gutter.** Templates set `--page-gutter` once. Feature code never sets horizontal page padding. Full-bleed parts (table rows, group headers) re-apply the same variable inside their cells.
5. **Sizes are on the grid or named.** Fixed widths, heights and icon sizes use a whole step of 4 up to 64 pixels, or a named size token (`row`, `control-md`, `sidebar`, `rail`, `header`, `assistant`, `companion`, `reading`, `overview`), or a fraction or keyword (`1/2`, `full`, `dvh`). No decimals. No arbitrary values.
6. **Changing the scale is a reviewed change** to this file and the lint configuration (section 1).
7. **Off-grid sizes, on purpose.** The 14 pixel small icon and the badge's 6 pixel gap and small padding are named tokens (`size-icon-sm`, the `badge-md` and `badge-sm` utilities, 6.13). Every other size is a multiple of 4.

Also required:

- **Hand-written CSS** passes `stylelint-declaration-strict-value`. Colours, margin, padding, gap, border radius, z-index, font size, box shadow and transition duration must be `var(--token)` or a keyword (`0`, `auto`, `inherit`, `currentColor`, `transparent`, `none`).
- **No inline `style` props** for spacing, colour, size or radius. The only allowed inline styles are CSS custom properties (for example `--row-index`) and values the virtualiser computes (a row's `transform` and `height`).
- **One icon module.** Components import icons only from `src/components/icons`. A restricted-import rule enforces it.
- **Banned packages** (lint and a dependency check): any second component base next to Base UI, any animated component set (Magic UI, Aceternity, React Bits), Vaul, any second icon set, any second text family.

### 4.4 One gutter and the left edge

## 5. Page templates

A template owns the gutter, the gaps and the slots. Feature code fills slots and adds no outer margin or horizontal padding. The page title lives once (8.6): the last segment of the header breadcrumb on list and overview pages, the title in the paper on document pages. It is the page's one `h1`. Home is the exception: it opens on its own title above the search field (Home P, the way product homes open on the work), so its `h1` is that visible title. Under the search field, and only while the person has a draft they have not submitted, Home shows Your drafts (8.13), the one part of Home that is the person's own; then the pulse strip, Last week in four quiet tiles (questions from AI agents, the share that found a matching fact, facts added or changed, the share of facts current), each a number, its change on the week before, one line of words and one small chart (7.1, "Chart"), the same for every person; then the quick actions and the one table. The change is a trend mark beside the tile's label. It is green or red only where the number has a good direction (the share that found a matching fact and the share of facts current, both better when they rise) and moved at least one point, and for the share that found a fact only when both weeks had at least 30 agent questions. Otherwise it is muted, as it always is for the two volumes, which have no good direction.

## 6. Tokens

The token file is one CSS file that defines every value below as a custom property under `:root` (light) and `.dark` (dark), plus the Tailwind `@theme` mapping (6.12). Semantic names follow shadcn so copied components work. The names shadcn does not define are additions: `--primary-hover`, `--brand-ink`, `--ink`, `--ink-foreground`, `--ink-hover`, `--selected`, `--scrim`, `--type-*`, `--hue-*`, `--tone-*`, `--status-*`, `--shadow-*`, `--duration-*`. Values are OKLCH, each fitted inside sRGB, with the exact hex beside it. Light is the default, dark is a full theme, and the person's choice (light, dark, system) is applied before first paint by a small script in the document head.

### 6.1 Colour

**Domain hues.** A ring of eight: teal 195, sky 236, indigo 272, violet 305, pink 350, lime 122, stone 70 (chroma x 0.32) and gray 262 (chroma x 0.16). One recipe, **Reference** (design round 3, the captain's image 1), makes the colours of every hue, so none looks louder than another: a very pale tint, a line one step darker, and one deep ink of the hue for the label and the mark alike (the `dot` token is the ink). Light tint `oklch(0.985 0.016c h)`, line `oklch(0.925 0.042c h)`, ink `oklch(0.43 0.125c h)`; dark mode has one neutral fill and line for every tone, `--badge-tint` `oklch(0.245 0.016 270)` #1d2028 and `--badge-line` `oklch(0.34 0.018 270)` #343842, and the hue is only in the ink `oklch(0.84 0.12c h)`. Kinds and statuses use the same recipe on their own hues (event 52, note 255, guide 152, example 300; success 150, warning 80, info 255, danger 27). Chroma is lowered where a value would leave sRGB. The light tint is barely there (1.0 to 1 against the page): a badge that asks for a look is carried by its line, its glyph and its ink, never by the fill alone. **The ring skips the alarm hues**: red and amber belong to state, so a domain never takes them. The name is always printed beside the domain mark. With more domains than hues, hues repeat in order of creation (open question 3).

### 6.2 Where kind, domain and status show in a list row

### 6.3 Contrast checks

Method: WCAG 2.x relative luminance from the 8 bit colour a browser paints, ratio (L1 + 0.05) divided by (L2 + 0.05), rounded down to one decimal so a number is never overstated. Text needs 4.5. Icons, dots, the focus ring and field boundaries need 3. Every OKLCH value is inside sRGB, and all 101 distinct non-alpha values were compared with what Chrome paints and matched within 1 of 255 per channel. Appendix B has the method. ### 6.8 Focus ring

### 6.11 Icons and fonts

### 6.13 Badges

Every tag in the product is one badge: a **mark** and a **label**. The mark is a 14 pixel icon (12 in sm), and every badge has one: the Heed domain mark for a domain, a clock for a date, a shaped glyph for a state or a type. Two sizes: md is 24 high with 8 padding, a 6 gap and a 13/16 label; sm is 20 high with 6 padding, a 4 gap and a 12/16 label, for every grid row (in every density), phone rows and menus. Radius 6 (`rounded-badge`). The label weight is 400; counts and avatar initials are 700. The component is `components/ui/badge.tsx`; the sizes are the `badge-md` and `badge-sm` utilities in `index.css`.

| Form    | Look                                  | Used for                                                                                             |
| ------- | ------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| soft    | tinted fill, 1px tint line, hue label | a domain (always) and anything that asks for a look: a status that needs action, a date near or past |
| outline | hairline, no fill                     | a plain fact: the kind where there is room, the quiet domain form                                    |
| bare    | mark and label, no box                | the same fact in a dense cell: accepted, ended, retired, plain dates, a domain inside a control      |
| solid   | ink fill                              | only a count that waits for this person                                                              |

**Tint means look at this.** In a healthy library a row has one tinted badge, its domain. Anything else is outline or bare until it needs attention.

**Reviewed before served is a line, not a badge** (D1, 18 October 2026). How a served fact was reviewed is the `ReviewStamp` (7.2): one quiet 12/16 line under the fact with the accepted mark, never a tinted or green badge, because every served fact has one and a healthy fact is never green (6.1). A badge would turn the proof into decoration on every row; a line reads like the commit line under a change in Linear, and it holds the person and the day, which no badge has room for. An edition label shows only on the Editions page (voice guide, principle 8). The `accepted` status badge keeps its job in lists (bare, 8.1).

**A domain's name and its room** (domain label decision, 18 October 2026). One rule wherever a domain is shown: the container decides how much of the name shows, the badge never leaves its box, and a shortened name always has the whole name one step away.

1. The badge has no width of its own beyond its name: it is as wide as the name up to the room its container gives (`min-w-0 max-w-full shrink`), so a wide place (a 480 panel, a phone row, a picker) prints the whole name.
2. With too little room the label ends in an ellipsis inside the badge; the box, its line and its mark stay whole, so the hue and the domain mark still say which domain it is. It never spills past a cell's padding or over a column line, and never overlaps the next column.
3. A cut name has the whole name in a tooltip (7.1, 350 ms) and sits over its row's link while it is cut, so a pointer can rest on it, as on the status glyph; a name that fits has no tooltip and lets the row take the click. A screen reader always hears the whole name, and the record the row opens prints it in full.
4. A row whose title is the point (the palette, an edition feed row, a compare step) caps the badge at one Domain column (192), so the title keeps its room.
5. A domain in a sentence is text: a mention chip wraps with the words around it, and a one-line control (a button, a role line, a reason line) truncates with the whole text in its tooltip. A count of more domains ("+2") names them in its tooltip and to a screen reader.
6. The Domain column is 192 (8.1): realistic names (about 22 characters, "Product & Subscription") print whole.

The word people read is **Domain**, everywhere (13, question 2). Code, the API and stored markup keep their internal names (`areaId`, `area_*` ids, `?area=`, `@area:`).

**Field provenance follows the attribute table.** The fields that carry a provenance mark, and the marks themselves, come from `src/domain/proposal-attributes.ts`, the one table the form and the agent tool share. ## 8. Written decisions

### 8.1 The library list: columns and the column budget

The list is a grid (direction A of the table design, made quieter by the professional pass, 8.12): data lines (`--border-subtle`) on both axes, a 36 high header of 12/400 muted labels with a field icon before every name but Title, a checkbox column that shows each row's kind until the row is hovered, focused or selected, titles at 14/400, virtual rows 40 high by default, an add row and a 36 high totals footer. It never scrolls sideways. Columns are chosen by the width of the list's container, so the sidebar, the assistant dock and a narrow window all behave the same way. The grid is for data surfaces only (tables and property lists); prose, forms, menus and cards keep one outer hairline and horizontal separators.

Rules:

- A column that does not fit does not scroll. Its data stays reachable: sorting, grouping and filtering still work on it, and the item page has everything.
- The column picker says "Not enough room at this width" for an option that does not fit.
- Header cells are buttons that sort. `aria-sort` is set. Numbers and dates use tabular numerals.
- The Status column is the status glyph alone (design round 2.1): seven statuses, seven shapes, warning-toned while it asks for a look and neutral otherwise (a healthy item is never green). The name is the glyph's accessible name and, with what it means, its tooltip. The narrow row keeps words for statuses that ask for a look; calm statuses keep their accessible named glyph; filters, chips and the item page spell the name out.
- The add row sits under the last data row and above the footer: a plus icon and "Add context" (bold muted text that turns foreground on hover) in the title column, hairlines like any row, the row height of the current density, a link to `/library/new`, shown to everyone who is signed in. It is outside the virtualized rows and `role=table`, and is not counted in the row count, the totals or select-all. On a narrow screen it is one full-width row.
- The totals footer (36 high, under the columns, in `text-caption` with the numbers bold) follows the search and the filters: items, domains, how many need a look, how many end within 30 days, owners. It sticks to the bottom of the window.
- Ended issues leave the default view (requirements 4.4, the Issue kind decision of the front end plan): an issue whose last day has passed is history. ## 9. Interaction rules

### 9.1 One command registry

Every action a person can take is a command in one registry (`src/commands`). The palette, the keyboard shortcuts, the cheat sheet, the action panel, row and bulk menus, tooltips with shortcut hints and the header buttons all read from it. Nothing else may bind a key or add a palette entry. A restricted-import rule keeps the hotkey library inside `src/commands`.

| Field                        | Meaning                                                                                                    |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `id`                         | Stable and dotted, such as `item.open` or `proposal.accept`                                                |
| `label`, `group`, `keywords` | Plain words, the palette group, and other names people search by                                           |
| `icon`                       | From the icon module                                                                                       |
| `shortcut`                   | Zero or more key sequences, shown by platform (Command or Control)                                         |
| `scope`                      | `global`, `list`, `document`, `review`, `overlay` (palette and menus), `selection` or `item`               |
| `when(context)`              | Returns visible, enabled or blocked with a reason. A role-locked command stays visible and explains itself |
| `run(context)`               | The action                                                                                                 |
| `undo`                       | Optional. Returns the reversal (9.4)                                                                       |
| `confirm`                    | `none`, `reason` or `type-to-confirm` (9.4)                                                                |

The type system rejects a command with no label or group. A test fails when two commands claim one shortcut in one scope. Shortcuts are single keys or `g` followed by a key (one second to finish). They are off while focus is in a field, except Escape and chords with Command or Control.

**The palette** opens with Command K or Control K, instantly with no animation. It searches items (a client index over title, id, about and owner, a target of 50 ms at the 95th percentile with 5,000 items), the catalogue's metrics and dimensions (`catalogue.list`, read once a person types and usually cached already; name, other names, Cube name and description), commands and places. When rows are selected or an item is open, the first group is "Actions for this item", which is the action panel.

### 9.3 Updates: optimistic or confirmed

Optimistic means the screen changes at once and rolls back with a message if the server refuses. It is allowed only for reversible actions that touch a person's own view or soft shared state.

| Mode                                                         | Actions                                                                                                                                                                                                                                                                         |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Optimistic                                                   | Filters, sort, view, density, column choices, selection, creating or deleting a saved view (delete has Undo), claiming or handing over a proposal, reading a notification, comment text before it is sent                                                                       |
| Confirmed by the server, with a pending state on the control | Submit, withdraw, accept, ask for changes, reject, retire, mark as checked (CON-211, it creates an edition), go back to an edition, change an area's state, use the stop switch, change a role or a limit, set aside a test question, any bulk action that writes governed data |
| Autosaved                                                    | Drafts (FR-110), 800 ms after the last change. The header shows "Saving..." then "Saved 14:02". A failure keeps the text on the device and shows "Not saved. Trying again", with a retry. Never a modal                                                                         |

A confirmed action shows a spinner on its button after 150 ms and holds it at least 300 ms. Its target is under 500 ms at the 95th percentile.

**Shown at once, then confirmed.** A decision on a proposal (accept, ask for changes, reject), single or bulk, shows at once: the proposal leaves To review and the counts, and its own page says the decision is being saved. The service still checks and publishes it; when it refuses, the proposal is back where it was, with the message. Nothing in a cache is changed meanwhile, so a list read again cannot undo it.

**Held, then sent.** A bulk decision in the review queue (FR-223) is confirmed first, with the plan the service reads for it, and is then held: its proposals leave the queue at once and the step waits behind an Undo toast (9.4) before it is sent. Undo cancels it before anything is written, so nothing governed is undone once it is made. While a step is held the browser asks before the page is left; leaving all the same sends it. The toast after it says what was decided, the edition and what was left out.

### 9.4 Undo and confirmation

- **Undo** is for reversible personal actions. The toast stays 8 seconds, pauses on hover and focus, and the action is reachable by keyboard. Command or Control Z within the window does the same.
- **Held steps** use the same toast: a confirmed bulk decision, or a confirmed discard of drafts from a list (8.13), waits behind Undo for the toast's 8 seconds and is sent when it closes (9.3).
- **Governed actions are not undone, they are confirmed first.** `ConfirmDialog` names the action in plain words, states the effect in one sentence, asks for the reason where the specification asks for one (a decision reason of at most 500 characters, FR-203), and labels the buttons with verbs ("Accept", not "OK"). A destructive confirm uses the tinted danger button. Focus starts on the reason field, or on Cancel when the action is destructive and has no reason field.
- **Type to confirm** (type the edition number) for going back to an edition, pausing an area and the stop switch. Deleting a domain asks for the words `permanently delete`, as AWS does, and is the one confirmation whose button stays disabled until the words match (`lockUntilTyped`): it takes everything under the domain with it, in one step that lists all of it first.
- **Blocked** actions stay visible with a reason (`BlockedButton`).

### 9.6 Item text and chip-aware inputs

**Item text is one document in a small safe Markdown subset** (FR-119), written in the same page editor for every kind: the summary (what agents read first, at most 280 characters) and the body are two zones of one document under a real title. The subset renders while it is typed: headings 2 and 3, bold, italic, bulleted and numbered lists of one level, links, inline code, code blocks and block quotes. The editor offers exactly three aids, each within the subset: Markdown shortcuts as you type (`## `, `- `, `1. `, `> `, three backticks, `**bold**`, `*italic*`, a code span), a slash menu (`/`) with those blocks, a template for the kind and a mention, and a selection toolbar (bold, italic, code, link, heading 2 and 3, mention; Alt F10 reaches it by keyboard). No images, no tables, no raw HTML, no nested lists; links open with `rel="noopener noreferrer"` and an external icon, because item text is untrusted data (NFR-024). The stored body is plain Markdown in the subset, written only when the person edits it, so the Source and History tabs diff it. A paste is read as Markdown in the subset and anything outside it stays the typed text; a paste longer than the summary keeps what fits, to a sentence end, and moves the rest into the body. A counter shows the size against the maximum.

**Short inputs may use chips and mentions.** Three inputs only:

1. `ScopeInput` ("where it applies"): a combobox with chips from the vocabulary (FR-107). Typing filters. Enter or a click adds a chip. Other names resolve to the main name and say so ("Norway, also called Norge"). Backspace on an empty input selects the last chip, then removes it. An unknown value is not accepted: "No match. An owner can add it to the vocabulary."
2. `SummaryInput` ("what happened", at most 280 characters, FR-118): one block. `@` offers metrics and `#` offers dimension values. Recognised words are underlined as suggestions ("Add Norway to where it applies?") and are never forced. Chips are plain text with a background. Paste is plain. Undo and redo work across chips. The counter counts visible characters.
3. The assistant composer: "About [name]" chips.

Chips are stored as plain text and as structured references, so the editor can be replaced. The spike chose a combobox with chips for `ScopeInput` and a one-paragraph ProseMirror editor (its own lazy chunk) for `SummaryInput`; the body is the same ProseMirror (`BodyInput`, its own lazy chunk), which keeps mentions as chips and writes them as `@[words](target)` tokens in the Markdown. The record and the results are in `docs/design/chip-input.md`. The behaviour above is the contract. Required before release: keyboard only works, VoiceOver and NVDA read "Net revenue, metric", 100 paste and undo cycles lose nothing, and the input works at 360 pixels.

### 9.7 The structured diff and the impact preview

The review page is the wide document page. It answers one question: should this change be accepted.

- **Main column, `FieldDiff`.** One row per field that changed, in the form's order. Each row has the field name, the live version and the proposed version side by side (stacked on phones, live above proposed). Prose uses a word level diff. A removal is struck through with a minus icon on a danger tint, an addition is underlined with a plus icon on a success tint, so colour is never the only sign. Where it applies is a `ChipDiff` (chips added and removed). Dates are a `RangeDiff` (before and after bars on one scale). Evidence is a `QuoteBlock` with the link, the quote and the date. Fields that did not change fold into "N fields unchanged".
- **A drafted proposal.** When an agent or the assistant drafted it with the proposer, the page is the page of any proposal: nothing says who wrote a field (quiet attribution is deferred to a later version, 6.13). The outside sources of its evidence, and their warnings, sit above the `FieldDiff`, and a flag keeps its soft badge under the proposed value.
- **Last row: "What an agent will see".** The agent-facing preview before and after, from the same code as the real reply (FR-108).
- **Rail.** `GateResult` lists the four check levels with the check name, a plain result and an icon. A failed required check blocks Accept: the button is a `BlockedButton` that says which check. `ImpactDelta` lists the test questions affected and every flip (fail to pass, pass to fail), with a cost estimate before a run (FR-516). Duplicates and conflicts follow.
- **Pass or fail comes from the fixed checks.** Any model written explanation is labelled as an explanation (FR-708).
- **`DecisionBar`:** Accept (ink), Ask for changes (outline), Reject (tinted danger). Each opens `ConfirmDialog` with a reason. The proposer and owner rule (FR-206) shows as a blocked button with the reason.
- **A proposal an agent or the assistant drafted.** The review page is the page of any proposal: the item as its title, its state badges, what changes, and one `DecisionBar`. Nothing on it says who wrote a field: no line beside a value, no glyph beside a name, no legend, no step trail of how the draft came to be, and the proposer's chip reads "Proposed by Priya Nair, 7 Oct 2026" (quiet attribution is deferred to a later version, 6.13). What the owner still needs stays: the outside sources of the evidence with their warnings, the soft flags under the values they are about, and the checks.

### 9.8 The assistant panel

- **Placement.** Docked on the right at 400, resizable from 320 to 560 by drag or by keyboard on the separator. Below 1280 it is a sheet. On phones it is full screen. It never overlays the page when docked.
- **One side panel at a time.** On a document page the assistant and the page rail share the aside slot. Opening one closes the other. Opened over a record's docked panel, the assistant takes its place; the record waits underneath, and closing the assistant shows it again with focus where it was. A record opened from a grid closes the assistant.
- **Content.** AI Elements conversation, prompt input and suggestions. Check results appear as tool results (check name and result), not as prose. It creates drafts and proposals only (FR-706). Each fact in the answer's facts read carries its `ReviewStamp` (7.2), the same line Try it shows, so "Checked before you saw it" (the citation check) and the stamp (the person's review before the fact was served) sit together as the answer's proof. An answer that found nothing ends in the `AbsenceLine` with Start a draft, never a question such as "Is something missing?".
- **Steps.** Above the answer a `StepTrail` lists the real steps its tools took, from the tool results, never from the model's words. A step's verb is in the present while it runs ("Reading eur-lex.europa.eu") and in the past once it is done ("Read eur-lex.europa.eu"); what it acted on (a site, a domain, an edition) is in the foreground colour and what it found follows a middle dot ("Looked up facts · 4 checked, 2 apply"). The running step turns the spinner and a done step shows its icon. While the answer works the trail is open; once it is done, two or more steps fold into one row that says how many there were and what they read ("2 steps · read 4 facts, 1 page") and opens again on a click. A step that did not work keeps the trail open and says "it did not work". A step that returned facts opens to them.
- **A change it proposes.** An answer that creates or changes something ends in a `ChangeCard` about that object, and the card is the Confirmation step that comes before a draft is created. It shows the item's kind glyph and title in 14/700; under them the "Unreviewed draft" badge, whether it is a new item or a change to an accepted one, and whether it is saved; every filled field read only, with its source where it came from a page, a fact, a gap or a default (FR-707), such as "From eur-lex.europa.eu", and never a mark that says the assistant wrote it or that the words are the person's; one line on what it left for them; and one decision, Not now (ghost) and Create draft (primary). Nothing is saved before Create draft. While it saves, the card's status region says "Saving the draft"; once saved, the fields fold under "What was saved" and Open draft is the one primary; when it was not saved, the card says nothing was saved and that the answer says why. Chat and meeting-summary capture land in the same card when they are built.
- **Turns.** Each turn says who wrote it. An answer starts with the assistant's mark (a pale Heed blue circle with the bot in the deeper blue, 32) and "Assistant" in 13/700; no edition shows there. The person's question sits on the right in a muted bubble under "You" and their initials on their own tint (32). Turns are 32 apart; the parts of one turn 8 or 12.
- **Answers.** An answer is GitHub-flavoured Markdown, read with a standard parser and drawn with React elements only, never as HTML (NFR-024): paragraphs, headings, lists (nested, task), tables, block quotes, code, bold, italic and strikethrough. A table whose delimiter line has not arrived yet waits as plain text while the answer streams. A table wider than the panel scrolls sideways inside the answer with its first column in view. A page of Heed, including a path written as plain words such as `/library?view=attention`, opens in the app; any other link opens in a new tab with an external icon. Raw HTML, images, footnotes and link definitions stay the text that was written. Item text keeps its own smaller subset (9.6).
- **Working state.** The trail's running step, then skeleton lines and the words "Working on it" in a status region. While a step runs, that line's spinner rests, so one spinner turns at a time. No gradient text and no looping decoration beyond the skeleton pulse and the spinner.
- **Limit reached.** An `Alert` says which limit and when it resets (FR-409).
- **One assistant, three states.** Closed, docked beside the page, or expanded to its own page (`/assistant` for Ask, `/try-it` for What an agent would get). Never two at once: on the assistant's pages there is no panel and no launcher. The conversation and the scope are the same in every state, and going from one to another loses neither.

  | From             | Action                                                       | To                                                                              |
  | ---------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------- |
  | Closed           | The launcher, Command or Control `\`                         | Docked beside the page, on the tab last shown                                   |
  | Closed or docked | The sidebar's Assistant, `g` then `a`, the panel's Open page | Expanded; the panel closes                                                      |
  | Docked           | Close, Escape, the launcher, Command or Control `\`          | Closed; the focus goes back to what opened it                                   |

- **Entry.** The sidebar's Assistant, for everyone, after Home, opens it expanded; `g` then `a` too, and on its page focuses the composer. An address without a scope takes the docked panel's, so expanding keeps it. The launcher: one round ink button in the bottom-right corner of every page signed in but the assistant's own (not the signed-out page), 40 (44 on phones), 16 from the corner and above the phone's home indicator. It toggles the docked panel, which has two tabs: Ask (the assistant) and What an agent would get (Try it). Connect your AI is a section of the person's own Settings, which What an agent would get points to. Beside a docked or overlaid panel it sits left of the panel; under a full-screen panel it hides. It rises 16 above any bar stuck to the bottom of the page (a list's totals, the selection bar), and toasts stack above it. The review's decision bar holds it instead (`AssistantBarButton`): the same round ink button, 32 (44 on phones), at the bar's end past a hairline, where the corner's launcher was, and the corner's launcher steps aside unseen while the bar shows, so toasts still rise over the bar. ### 9.9 Forms

Labels sit above fields in `text-body` 700 (6.5). A hint sits under the label in `text-caption` muted. An error sits under the field in `text-caption` with the danger icon and `--status-danger-fg`, and links to the field through `aria-describedby`. Optional fields say "optional" in words, with no asterisks. Validation runs on blur, then on change once an error has shown. More than two errors add a summary at the top with links. The form asks for the six things of FR-104 in that order, with the last three under the same heading style. Submit is never disabled for being incomplete: it shows the errors. It is blocked only when a check fails.

**An optional field that guides** (`CaveatField`, "What not to conclude", FR-104, decided 18 October 2026). It is drawn at the rail's real 320 pixels and keeps five groups, 24 apart and 12 inside a group: the heading with "Optional" in words where a needed section shows Needed, and one help sentence; a box that grows from three rows, with no placeholder (an example in a placeholder reads as a value already filled in); three sentence starters as small outline buttons that put the opening words in the box after what is there, with the caret after them; one example for the item's kind in quotes with a quiet "Use this" link; and, always visible, one sentence on what happens to the line, then the live card. The card, "What an agent gets", is a bordered card on the card surface with a caption strip: the item's title, a hairline, the line after "What not to conclude:" or, with the box empty, what an agent assumes instead. It follows the box as the person types, with no save, and is not a live region, so a screen reader is not interrupted at every key. A disclosure, "Show what the app receives", shows the one field as the app receives it in mono on the muted fill. ### 9.11 Where am I and how to get back

**One crumb tree.** `src/web/lib/crumbs.ts` defines every route: its label, the page above it, and whether it is a record page; an old address that only redirects and the pages with no shell (signed out, the agent's consent page) are listed as exempt by name. A route without a definition fails the type check, and `tests/unit/crumbs.test.ts` checks the tree against the generated routes. The trail is hierarchy, not history:

- The root crumb is the sidebar place, named from `nav.ts`, so a rename renames the crumb. There is no Heed or Home root above it.
- A view or section is a crumb only when it has its own navigation entry: the library's views in the sidebar, the Settings sections, and the Administration sections for the people who have their list. Health's compare focus, a mode, names itself too. Chips, tabs, filters and Feed or Table are not crumbs; the page shows them.
- Opening a record in the docked panel does not change the trail; the panel's bar names the record.
- The final crumb is the page title on a list or overview page, and the record's short identity on a record page (8.6). An address no page answers to ends with Page not found under its place.
- Every crumb above the page is a link. A list reopens with the view, search, filters and sort the person last used there in this tab, without the open panel; an item page that carries its list in its address reopens that list. The scroll position is kept per list (the address without the panel's parameters), so the list comes back where it was left.

**History.** One table, so every screen does the same:

| ------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| Go to another page: the sidebar, a link, the palette, a `g` chord, a crumb, a panel's expand                                                      | New entry                                             |
| Open a record in the docked panel when none is open                                                                                               | New entry, marked as the panel's                      |
| Step to another record: j and k in a panel, Previous and Next, j and k on an item page or in the review queue, the next proposal after a decision | Replace, keeping what the entry says                  |

**Going back on screen.** A way back goes back only when the entry it means is directly behind the one on screen: the router's index says an entry is behind (the first entry of a tab has none), and the entry's own state says what it was opened from (`lib/history.ts`), never `window.history.length`. Closing a panel goes back when its entry opened it over the list. Going up from a record expanded from its list's panel (Escape, or `‹ parent` on a phone) goes back to that list, panel and scroll as they were; from anywhere else it is a new entry to the parent crumb. On a list page with nothing open, Escape only clears the selection and the cursor.

**Back to origin.** The trail is hierarchy; a record reached sideways (What changed to an item, an edition to a metric, Health to an item, the palette to a record) also leads back to where the person was. Every entry of the tab says in its history state which page it was opened from: its address (path and search, nothing else) and its place in the tab's history (`lib/history.ts`). A new entry for another page was opened from the entry behind it; a new entry for the same page (a filter, a view, a panel) and a replaced one keep the origin the page had. The origin's name is worked out by matching that address against the route table: it is the origin page's own final crumb (`What changed`, `Editions`, `2026-10-06.2`, `Home`), so nothing in the address or the state can name it or lead outside Heed, and an address no page answers to, an old one that only redirects, or a form (once sent there is nothing to go back to) is no origin.

- On a record page, and on What changed, whose origin is not on its trail, `← origin` sits before the trail; with the origin on the trail the crumb is the way back, so the two never point at the same place.
- It, and Escape on a record page, go back when the origin is the entry directly behind, so its panel, filters and scroll come back exactly; otherwise (a filter changed since) they open the origin as a new entry.
- A deep link, a new tab and the first entry of a tab have no origin: the trail is the way back. A reload in the same tab keeps it.
- On a phone it is the one control beside the menu: `‹ origin`, else `‹ parent`.

## 10. Motion

1. **CSS first.** Transitions and the library's start and end style attributes. A script animation library is allowed only for the assistant dock and list reordering, through `LazyMotion`, and only if CSS cannot do it.
2. **Properties.** Only `opacity` and `transform`, plus colour on hover. `width` and `height` are allowed only for the docked assistant, the sidebar and collapsibles. Never `transition: all`. Name each property.
3. **Durations.** 100, 150 and 200 ms from 6.9. Exits are 100 ms.
4. **No choreography.** First load and route changes do not animate. A shared element transition between list and item is a later option.
5. **Keyboard actions do not animate.** Cursor movement, selection toggles, the palette opening and closing, and the sidebar shortcut are instant. One exception: Command or Control backslash opens and closes the assistant's docked panel with the same motion as the launcher, because a panel sliding in is not cursor movement.
6. **Only two things loop**: the skeleton pulse (opacity 1 to 0.5 and back over 1.6 s, `--animate-pulse`) and a spinner. Nothing else.
7. **Delays.** A loading indicator waits 150 ms and then stays at least 300 ms. A tooltip waits 350 ms. A toast stays 5 seconds, or 8 with Undo. Inside one assistant answer, the rows that close it follow it by 80 and 160 ms (rule 10).
8. **Press.** Buttons and icon buttons scale to 0.97 for 100 ms. Rows, chips and menu items do not.
9. **Reduced motion.** With `prefers-reduced-motion: reduce`: transforms go, entering and leaving become opacity fades of at most 100 ms, the skeleton is static at 70 percent opacity, the spinner becomes the words "Working" in a status region, smooth scrolling is off.
10. **An assistant answer arrives, then rests.** Only what has just come in moves, and only while the answer arrives; a conversation opened again does not move. The question just sent rises into place at the top of the view, 16 below the panel's tabs or the page's header. The newest answer keeps room under its question, so the question always reaches the top, and the view never scrolls while the answer grows; an older answer gives the room up when the next question is sent. Each checked sentence settles in as the service lets it out: a new block rises 4 pixels as it fades in, words added to a block only fade, and what was on screen stays. A step row enters in the present tense, its spinner fades into its icon as its verb turns to the past, and its counts fade in; the skeleton fades out as the first sentence lands. Once the answer is done a trail of two or more steps folds into its one row by its height. With less motion the running step's spinner is a still ring, and its verb in the present says it is working. The facts read, the checked row and the actions fade in one after another once the answer is done. While the end of the newest answer is more than 100 below the fold (the panel's bottom edge, or the page's composer bar), a Latest pill at that edge goes to it; it is no live region. With less motion each of these is a fade of 100 ms without delay (rule 9). A block that rises as it arrives must not change a measurement: the answer's fold reads the words' layout height (`offsetHeight`), never the frame's scroll overflow, which the rise inflates for a moment without resizing anything, so a short answer never stays folded behind Show the rest of the answer.

### 12.3 The left-edge and geometry test

Elements carry data attributes. The test reads `getBoundingClientRect()` for each template state at each of the three widths.

- `data-edge="start"` on the first element that defines the left gutter edge: the header's first element, the toolbar's first control, the checkbox cell of a grid row (the table frame's left edge; the kind icon sits 40 in) or the kind icon of a narrow row, a group header label, the footer text, a section heading, the first card, the paper. - `data-centre` on the cells and controls inside one row or one toolbar row: their vertical centres are within 0.5 pixel, and siblings in a toolbar have the same top and height.

## 13. Open design questions

These need a person. Each has a recommendation, and the contract works with the recommendation until it is answered.

1. **Kind display names.** The specification's kinds are Event, Note, Guide and Example. The prototypes said Situation, Definition overlay, Playbook and Verified example. The specification also says definitions stay in the source tool (section 1.5 of the specification, FR-210), which a "definition overlay" may contradict. Recommendation: use the specification's words, and keep the colours and glyphs.
2. **Domain or Area.** _Decided (18 October 2026):_ Domain is the one word people read, in the app, its messages and, with the server's wording, the specification's glossary. Internal names, ids, the `?area=` address and the stored `@area:` markup stay.
3. **Nine areas, five hues.** The first deployment lists nine areas in the specification, and the contract has five domain hues, of which one is gray and four are colours. Recommendation: let hues repeat in registry order, since the name is always printed. If repeats confuse in the filters, add up to three hues from the same recipe.
4. **What the "default" domain is.** The quiet text and badge rule needs it. Recommendation: the viewer's own domain, taken from the area they own or last contributed to. It needs a profile field.
5. **The Cards view.** Round 5 proposed Cards as a second browse view. The contract keeps it out of the first build. Recommendation: later, after the list is polished.
6. **Field boundaries at 3 to 1.** Inputs get a visibly stronger border than the prototypes (3.1 to 1 in light) to meet WCAG 1.4.11 under NFR-111. Recommendation: accept. The alternative is a lighter border and a written exception to NFR-111.
7. **The docked assistant.** The research prefers docked and resizable, and round 5 floated it. Recommendation: docked, with the sidebar collapsing to the rail when it opens below 1600 wide.
8. **Which bulk actions exist.** _Decided:_ the library offers Copy links and Clear; the review queue offers the decisions and Assign in bulk (FR-223). Each proposal keeps its own decision and checks, a proposal the person proposed, one with a failed required check or one that changes an item another selected proposal changes is left out and named, and the accepts of one kind are one edition.
9. **Owner review on a phone.** The specification says owner review may need a larger screen. The review page stacks on phones and passes the three screenshot widths, but its decisions are not designed for a thumb. Recommendation: allow it, and test with one owner.
10. **Markdown subset and the plain text field.** The product owner's direction says item text is Markdown with a preview. FR-119 says a plain text field with a preview. Recommendation: both are met by a plain field that renders the subset in 9.6. Confirm the subset.
11. **What counts as Needs a look.** Round 5 asked whether it should include items with an edit waiting for the person looking. Recommendation: re-check due, source changed, source missing, changes requested, and edits waiting for the viewer.
12. **Efferd free blocks.** _Answered (17 Oct 2026):_ Efferd's terms (efferd.com/terms, updated 15 September 2026) let free blocks be used the same way as paid ones (changed and shipped to customers) and forbid passing the library on as a kit. Efferd stays a reference only: the shell is built from shadcn blocks, and Heed copies none of Efferd's code or assets.

## Appendix B. How the numbers were checked

- **Contrast.** A script converts each OKLCH value to sRGB, fits chroma so the colour is inside sRGB, rounds to 8 bits, and computes WCAG 2.x contrast from the 8 bit values. Round 5's own table was reproduced first (for example white on the event tile 4.2 and on the guide tile 4.0), then the pairs in 6.3 were added.
- **Browser check.** All 105 non-alpha token values were set as `fillStyle` on a canvas in Chrome and read back. Every channel matched the computed hex within 1 of 255. The two `--selected` values were then computed from `color-mix(in oklab, ...)` and read back the same way; since the accent (12 Oct 2026) they are plain OKLCH values.
- **What the audit found in round 5's tokens.** Field boundary 1.4 to 1 in light and 1.6 in dark (needs 3). Light domain dots at 2.2 (amber) and 2.9 (teal) against the page (a dot is 8 pixels and needs 3). Light warning status dot 2.4. Several values outside sRGB. These were adjusted in section 6, and the other values are round 5's.
- **Lint patterns.** The patterns of 3.3 were run against 59 violating and 58 compliant class names, including variants, `!` modifiers and arbitrary variants.
- **Column budget.** The table in 8.1 comes from the widths in the same section. The arithmetic is sidebar plus gutters plus the Title minimum plus the visible columns.
- **Not measured.** No component exists yet, so no pixel was measured in a built screen. The column widths, the toolbar fold width and the heights are budgets to be confirmed by the geometry test in the first build. The contract treats a failing budget as a reason to change the budget in this file, not to work around it in a screen.
- **Sources carried over, not linked.** The HTML prototypes of rounds 4 and 5 (structure, density, colour and the audit of what looked off), the front-end research report (toolkit, guard rails and standards), and the requirements specification (what the product must do).
